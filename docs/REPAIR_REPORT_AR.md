# نتيجة فحص وإصلاح نظام إدارة الحالات المدرسية

استند العمل إلى ملفي SRS وSchool Disciplinary Management System Prompts المقدمين. النصان محفوظان في مجلد docs. ملف SRS نفسه مسودة تتطلب اعتماد المدرسة؛ الإصلاح البرمجي لا يحل محل اعتماد إجراءات المدرسة.

## النواقص التي عولجت

| النقص | ما أضيف أو أصلح |
| --- | --- |
| إعداد المشروع لا يكفي لتثبيت وتشغيل المصدر | استعادة package.json والاعتمادات وأوامر التطوير والبناء والفحص وملف البيئة |
| خلط ملفات البناء مع المصدر | إزالة مخرجات البناء وملف قاعدة SQLite من الشجرة وإضافة قواعد التجاهل |
| قاعدة البيانات لا تطابق متطلبات PostgreSQL | مخطط وتهيئة PostgreSQL، وأرشيف لترحيل SQLite القديم، وcompose.yaml للتطوير |
| بعض مسارات API غير محمية بالصلاحية المناسبة | التحقق من الجلسة الحالية والدور وملكية الحالة أو إسنادها قبل الوصول |
| احتمال استمرار صلاحية الحساب بعد تعطيله | فحص حالة الحساب الحالية في كل طلب محمي |
| لوحات متابعة بأرقام ثابتة | إحصاءات وقوائم فعلية من قاعدة البيانات بحسب صلاحية المستخدم |
| روابط تفاصيل الطلاب والموظفين والملف الشخصي | إضافة صفحات التفاصيل والملف الشخصي وسجل الحالات المتاح للمستخدم |
| مراجعة المدير لا تنفذ القرار بشكل متسق | حفظ القرار والتكليف أو الإغلاق وسجل التدقيق معًا داخل transaction |
| إمكانية ترك مراجعة ناقصة عند فشل طلب التوضيح | حفظ التوضيح وتغيير الحالة وسجل التدقيق في عملية واحدة |
| نقص عرض التسلسل التاريخي | إضافة API وعرض سجل الحالة دون كشف محتوى الملاحظات السرية |
| اختلاف أسماء حقول النماذج عن API | إصلاح نماذج الإجراءات والتدخلات والمتابعة وحقول التواريخ والأسماء |
| البحث الظاهر في الحالات لا يطبق الفلتر | ربط البحث بالخادم مع إبقاء نطاق صلاحيات المستخدم |
| مخاطر كشف محتوى الحالات للمسؤول التقني عبر التدقيق | حجب بيانات metadata عنه مع بقاء معلومات الحدث التقنية |
| مشاكل التصدير | تصحيح الرابط واقتباس CSV والحماية من صيغ الجداول، وحصر التصدير بالمدير |
| نقص التحقق الآلي | GitHub Actions مع PostgreSQL 16 واختبارات الوحدة والتكامل والأمان والمتصفح |
| غياب مسار لإنشاء أول مدير حقيقي | أمر admin:create دون تحميل بيانات طلاب تجريبية |
| تنبيه أمني في اعتماد غير مباشر | تحديث deepmerge-ts ضمن إعداد Prisma والتحقق من npm audit |

## ما يلزم توفيره قبل تشغيل المدرسة

1. استضافة التطبيق وPostgreSQL، ورابط HTTPS النهائي، وقيم DATABASE_URL وSESSION_SECRET. هذه قيم خاصة لا توضع في GitHub.
2. اسم وإيميل ورقم الموظف لأول مدير وكلمة مرور قوية؛ يدخلها المسؤول عبر أمر admin:create.
3. بيانات الطلاب والموظفين الحقيقية، وتصنيفات المخالفات والإجراءات والتدخلات المعتمدة. بيانات seed تجريبية فقط.
4. اعتماد مصفوفة الصلاحيات وسياسة إغلاق الحالات والملاحظات السرية وحقول التصدير من المدرسة.
5. وجهة النسخ الاحتياطي والتشفير وفترة الاحتفاظ وتجربة الاستعادة، وتحديد حد محاولات الدخول المشترك على الاستضافة.
6. إذا كانت هناك بيانات قديمة في SQLite: ترحيلها المنفصل بعد نسخة احتياطية. الترحيل الجديد ينشئ PostgreSQL فارغًا ولا ينقل سجلات SQLite تلقائيًا.
7. تجربة قبول مع المدرسة على بيانات وهمية، بما فيها الجوال والطباعة والتزامن وجميع تسلسلات العمل المطلوبة.

## حدود هذا التسليم

- دُمجت التغييرات في main عبر طلب السحب #1، ثم أُضيف تحسين الواجهة وإصلاحات إضافية عبر طلب السحب #2؛ لم يجر تشغيل نظام إنتاج أو نقل بيانات حقيقية.
- تصدير الملاحظات السرية معطل لحين اعتماد سياسة واضحة.
- الإشعارات البريدية واستعادة كلمة المرور والمرفقات تحتاج مسارات وخدمات إضافية إذا قررت المدرسة إدراجها؛ لا توجد مفاتيح خدمات وهمية تعوض عنها.
- الحماية من محاولات الدخول داخل التطبيق محلية لكل عملية تشغيل؛ النشر بعدة نسخ يحتاج حماية مشتركة على مستوى الاستضافة.
- نجاح الاختبارات لا يعني تغطية كل المتطلبات غير الوظيفية أو اعتماد جاهزية التعامل مع بيانات طلاب حقيقية. نتائج الفحص الدقيقة في REPAIR_STATUS.md.
