Prompt 1
I am developing a full-stack web application called 
School Disciplinary Management System (SDMS)
. Use the attached Software Requirements Specification (SRS) as the primary source of truth.
The application will allow teachers to report student disciplinary incidents, the principal to manage staff access and review all cases, and the school counsellor to document interventions and follow-ups. Authorized users must be able to export approved records to CSV.
Technology stack:
Next.js with TypeScript
Tailwind CSS
PostgreSQL with Prisma ORM
Secure server-side authentication and role-based access control
Zod for validation
Recharts for dashboards
Vitest
 and Playwright for testing
Before implementing anything:
Analyze the SRS and extract all functional requirements, non-functional requirements, business rules, user roles, and acceptance criteria.
Identify ambiguities, contradictions, and missing decisions. Do not silently invent school policies.
Propose a modular architecture, database entity relationships, application routes, API endpoints, permissions matrix, and implementation roadmap.
Identify the minimum viable product (MVP) and separate it from optional future features.
Establish a requirements traceability matrix mapping every SRS requirement to planned components and tests.
Create a maintainable project structure and document the architecture in README.md and the implementation plan in docs/implementation-plan.md.
Do not build the entire application in one response. First provide the analysis, architecture, and unresolved questions. Wait for my approval before proceeding to implementation.
Important constraints:
PostgreSQL must be the authoritative data store; CSV is only for authorized export.
Never use mock data as a substitute for required backend functionality.
Never rely on frontend-only permission checks.
Do not implement AI-generated punishments or automated disciplinary decisions.
Do not expose sensitive student records in logs, URLs, or unauthorized exports.

Prompt 3
Implement secure authentication and authorization for the SDMS using the existing project architecture.
Create three primary application roles:
1. Principal / Super Admin
Approves, rejects, deactivates, and reactivates staff accounts.
Can view and manage all cases within the school.
Can review complaints, request clarification, assign cases, record decisions, approve actions, close or reopen cases according to policy.
Can access audit logs and authorized CSV exports.
2. Teacher
Can access the portal only after account approval.
Can submit incident reports linked to valid students.
Can view their own submitted reports and authorized status updates.
Cannot access unrelated cases, confidential counselling notes, administrative controls, or unrestricted exports.
3. Counsellor
Can access cases permitted by the configured school policy.
Can document counselling sessions, interventions, and follow-ups.
Cannot approve staff accounts or perform principal-only actions.
Implement:
Secure login and logout.
Password hashing using a suitable established library if password-based authentication is selected.
Secure, HTTP-only, appropriately configured session cookies.
Server-side role and record-level permission checks.
Protected routes and APIs.
Account approval and deactivation enforcement.
Session expiration and safe authentication error handling.
Audit events for account approvals and other significant security events.
Do not create a public self-registration flow unless explicitly approved. Use an administrator-approved invitation or onboarding mechanism.
Test unauthorized direct API calls, privilege escalation attempts, inactive accounts, and cross-user record access. A hidden button or protected frontend page alone is not sufficient security.
Integrate the implementation with the existing database and frontend. Document the environment variables and secure setup process. Never hardcode production credentials.

Prompt 5
Implement the complete disciplinary incident and case management workflow in the SDMS.
Teacher workflow
Search for a student using an approved identifier.
Submit an incident report with the incident date, category, description, and required fields.
Receive a unique case reference.
View the submitted report and its current status.
Respond to authorized clarification requests.
View permitted updates after review or action.
Principal workflow
View newly submitted cases.
Review the incident details.
Request clarification, assign the case, record a decision, or take another approved action.
Record the decision rationale and responsible staff member.
Approve or record school-authorized disciplinary measures.
Monitor interventions and follow-ups.
Close or reopen cases with a recorded reason.
Counsellor workflow
View cases allowed by the configured permissions.
Record counselling sessions and intervention plans.
Assign follow-up dates and responsible staff.
Record progress and outcomes.
Mark follow-ups completed or identify additional support required.
Implement explicit status transitions, such as:
Submitted → Under Review → Clarification Required or Assigned → Action Pending → Follow-up Pending → Closed.
Adapt this example to the approved SRS. Support rejection or closure without further action where school policy allows it.
Every important event must record the acting user, timestamp, affected case, and relevant change. Prevent unauthorized transitions, duplicate submissions where feasible, and concurrent updates from silently overwriting one another.
Important:
A reported allegation is not automatically an established finding.
Account approval is separate from case approval.
Record the action and rationale without assuming that every complaint requires punishment.
The system must not automatically determine guilt or sanctions.
Confidential counselling notes must follow their own permissions.
Implement backend logic, database persistence, frontend integration, and automated tests for normal workflows, invalid transitions, and unauthorized access. Demonstrate the workflow using fictional test data.
Prompt 6
Implement production-quality CSV reporting and audit logging for the SDMS.
CSV reporting requirements
Allow authorized users to filter records by date range, case status, incident category, class, and other approved fields.
Generate CSV exports from PostgreSQL data, not from frontend tables or manually maintained files.
Use a consistent schema, UTF-8 encoding, and documented date formats.
Support correct handling of commas, quotation marks, newlines, and Unicode text.
Apply backend authorization to every record and field before export.
Exclude confidential counselling notes and other restricted fields unless explicitly authorized.
Add a clear warning before downloading sensitive student data.
Mitigate CSV formula injection in untrusted values.
Use pagination, streaming, or sensible export limits for large datasets.
Log the exporting user, timestamp, applied filters, export scope, and result.
Audit logging requirements
Record staff account approvals and deactivations.
Record incident submission and significant case modifications.
Record case status changes, assignments, decisions, actions, and closure or reopening.
Record intervention and follow-up changes, respecting the confidentiality of the underlying content.
Record successful exports and relevant failed attempts.
Protect audit records from modification by ordinary users.
Create tests proving that a teacher cannot export other teachers' cases, a counsellor cannot export restricted notes, and the principal can export only fields allowed by the approved policy.
Provide a documented example CSV schema and fictional test exports. Never use real student information in development samples.
